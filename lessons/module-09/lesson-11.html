Documentation and Schematics

Professional documentation is as important as the circuit itself. Well-drawn schematics communicate design intent, enable efficient debugging, and support manufacturing. This lesson covers schematic best practices, documentation standards, and what information hardware engineers need to capture.

Goal
Communicate design clearly and completely
Audience
Future you, colleagues, manufacturing, support

Schematic Drawing Standards

Schematic Best Practices

Rule Reason
Power rails at top, ground at bottom Universal convention, easier to read
Signal flow left to right Matches reading direction, shows processing order
No 4-way wire junctions Ambiguous whether connected or crossing
No diagonal wires Harder to follow, looks unprofessional
Label all components Reference designators needed for BOM, assembly
Include component values Essential for debugging, doesn't require BOM lookup
Group by function Easier to understand subsystems
Use net labels for complex routing Reduces wire clutter, clearer connectivity

Reference Designators

Prefix Component Type
R Resistor
C Capacitor
L Inductor
D Diode (including LEDs)
Q Transistor (BJT, MOSFET)
U Integrated Circuit
J Connector (Jack)
SW Switch
F Fuse
Y Crystal/Oscillator
TP Test Point
Numbering Convention: Number components sequentially by location on schematic (left-to-right, top-to-bottom) or by functional block. Be consistent throughout the project.

Essential Documentation Package

Document Content Audience
Schematic (PDF) Complete circuit with all values, notes Engineering, test, support
Bill of Materials (BOM) Part numbers, quantities, suppliers Purchasing, assembly
Assembly Drawing Component placement, polarity marks Assembly technicians
Fabrication Drawing Layer stackup, drill chart, notes PCB fabricator
Test Procedure Step-by-step verification process Test technicians, QA
Design Notes Calculations, design decisions, rationale Future engineers, yourself

BOM Best Practices

Column Purpose
Reference Designator Links to schematic (R1, C2, U3)
Quantity Total count per board
Description Human-readable component description
Value Component value (10kΩ, 100nF)
Footprint/Package Physical size (0603, SOIC-8)
Manufacturer Component manufacturer name
Manufacturer Part Number Exact MPN for ordering
Supplier/Distributor Digi-Key, Mouser, etc.
Supplier Part Number Ordering code
DNP/Populate Whether to assemble (Do Not Populate flag)
Obsolescence: Include alternate part numbers for critical components. Parts go obsolete without warning. Having approved alternates prevents production delays.

Design Notes to Capture

Why Document?
You will not remember in 6 months
What to Capture?
Decisions, alternatives considered, calculations

Essential items to document:

  • Why specific component values were chosen (not just what)
  • Operating conditions and assumptions
  • Calculations (gain, filter cutoff, timing)
  • Design margins and worst-case analysis
  • Alternative parts considered and why rejected
  • Known limitations or issues to address in next revision
  • Test results from prototypes

Version Control

Item Best Practice
Schematic revision Rev A, B, C... on title block, increment for any change
PCB revision Silkscreen marking, may differ from schematic rev
BOM version Date and revision in filename/header
Change log Document what changed between revisions
File naming project_revX_YYYYMMDD.ext format
